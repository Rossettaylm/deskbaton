# 泰坦军团 P275MV DDC 实测（2026-10-16）

环境：MacBook Pro 14"（Mac15,7，Apple M3 Pro，36 GB），macOS 15.7.4；合盖（`AppleClamshellState = Yes`）；单台外接 P275MV 作主屏。这是设计文档中的目标硬件。

`set-input` 和 Windows 端尚未测：合盖时切走画面，本机没有内建屏可回退。

## 显示器识别

`deskbaton-cli displays`：

| 字段 | 值 |
|---|---|
| EDID UUID | `31035990-0000-0000-1022-0104B53C2278` |
| 厂商 / 型号 | LHC / P275MV |
| 序列号 | `0000000000000`（全零，同型号多台时无法靠序列号区分） |
| 屏幕模式 | 1920×1080（渲染 3840×2160）144 Hz |

`system_profiler` 只列出这一台外接屏，与合盖状态一致。

## 当前接法（本机侧）

- 画面：P275MV 是唯一显示器，接法为单根 USB-C（视频 + USB + 65W PD）。
- 键鼠经显示器 USB 集线器接到 Mac：Genesys Logic USB2.1 Hub（`05e3:0610`）→ VIA Labs USB2.0 Hub（`2109:2817`）→ SONiX Gaming Keyboard、ASUS ROG OMNI RECEIVER。
- 结论：此刻 KVM 的 USB 上行走的是 Mac 这一路（USB-C）。

## 读取输入源（VCP `0x60`）

### 现象

原实现（发一次 Get VCP 请求，等 50 ms 读回包，失败时整轮重试 3 次）在这台显示器上几乎总是失败；当天只有一次成功（读到 `0x0F`），推测是恰好有 BetterDisplay 在同一时刻发了同样的请求。退出 BetterDisplay、拔插 USB-C 都不改变结果。

### 原始字节探针

用独立的 ObjC 探针在同一个 `IOAVService` 上发请求、逐次打印每次读的 11 字节（缓冲区预填 `EE`）：

| 请求方式 | 第 1 次读 | 之后不重发再读 |
|---|---|---|
| 发 1 次 | `6E 80 BE` + 乱码（3 次运行 0/3 合法） | 乱码 |
| 连发 2 次，间隔 10 ms，等 50 ms | `6E 88 02 00 60 00 00 0E 00 0F D5`（3/3） | 乱码 |
| 同上，等 100 ms | 合法（2/2） | 乱码 |
| 同上，读 VCP `0x10` 亮度 | 合法 2/3，当前 `0x64`、最大 `0x64` | 乱码 |

结论：

- **P275MV 只收到一次请求时回 Null Message（`6E 80 BE`），连发两次才回值。** 这与 MonitorControl 在 Apple Silicon 上的做法一致。
- Null Message 只有 3 字节，缓冲区其余部分是总线残留；之前把尾部当成「上次回包的残片」是误判。
- 不重发请求而再读，读到的不是回包而是残留数据。所以「读到 Null Message 只再读、不重写」是错的，每次重试都要重新发请求。
- 偶发失败（亮度 1/3）靠整轮重试兜住。

### 修复与验证

`deskbaton_ddc_transact`：在同一 `IOAVService` 上把请求连发 2 次（每次前等 10 ms），等 50 ms 读一次；Rust 侧把 Null Message 归为未就绪，整轮最多重试 3 次。`set_input` 也改为连发 2 次（Set VCP 重复执行无副作用，但切换效果还没在本机实测）。

修复后连续 10 次 `deskbaton-cli get-input` 全部返回 `0x0F`。

HP D27k 尚未用新实现复测。

### 回包含义

| 字段 | 值 | 说明 |
|---|---|---|
| 当前值 | `0x0F` | 业界常见 **DP-1** 编码 |
| 最大值 | `0x0E` | 小于当前值，不能当「合法编码上限」用 |
| 类型 | `0x00` | 显示器把 `0x60` 报成「设置参数」类型 |

## 对设计假设的含义

设计文档（§3）尚未验证的两项：

| 假设 | 本次观察 | 状态 |
|---|---|---|
| USB-C = `0x1B`，DP = `0x0F` | Mac 走 USB-C，读到 `0x0F` | **与常见值不符**。这台显示器很可能把 USB-C（DP Alt Mode）报成 DP。DP 口（Windows）的编码仍未知，两个口有可能撞码；撞码时「持棒判定」不成立。 |
| KVM 跟随输入源 | 画面在 Mac 时，键鼠也在 Mac 的 USB 树上 | 只说明这一侧一致，切到 DP 后键鼠会不会离开还没测。 |

在 DP 口的编码读到之前，不改设计文档的默认 `input_code`。
