# 泰坦军团 P275MV DDC 实测（2026-10-16）

环境：MacBook Pro 14"（Mac15,7，Apple M3 Pro，36 GB），macOS 15.7.4；合盖（`AppleClamshellState = Yes`）；单台外接 P275MV 作主屏。这是设计文档中的目标硬件。

`set-input` 和 Windows 端尚未测：合盖时切走画面，本机没有内建屏可回退。

## 显示器识别

`deskbaton-cli displays`：

| 字段 | 值 |
|---|---|
| EDID UUID | `31035990-0000-0000-1022-0104B53C2278` |
| 厂商 / 型号 | LHC / P275MV |
| 序列号 | `0000000000000`（全零，同型号多台时无法靠序列号区分） |
| 屏幕模式 | 1920×1080（渲染 3840×2160）144 Hz |

`system_profiler` 只列出这一台外接屏，与合盖状态一致。

## 当前接法（本机侧）

- 画面：P275MV 是唯一显示器，接法为单根 USB-C（视频 + USB + 65W PD）。
- 键鼠经显示器 USB 集线器接到 Mac：Genesys Logic USB2.1 Hub（`05e3:0610`）→ VIA Labs USB2.0 Hub（`2109:2817`）→ SONiX Gaming Keyboard、ASUS ROG OMNI RECEIVER。
- 结论：此刻 KVM 的 USB 上行走的是 Mac 这一路（USB-C）。

## 读取输入源（VCP `0x60`）

### 现象

原实现（发一次 Get VCP 请求，等 50 ms 读回包，失败时整轮重试 3 次）在这台显示器上几乎总是失败；当天只有一次成功（读到 `0x0F`），推测是恰好有 BetterDisplay 在同一时刻发了同样的请求。退出 BetterDisplay、拔插 USB-C 都不改变结果。

### 原始字节探针

用独立的 ObjC 探针在同一个 `IOAVService` 上发请求、逐次打印每次读的 11 字节（缓冲区预填 `EE`）：

| 请求方式 | 第 1 次读 | 之后不重发再读 |
|---|---|---|
| 发 1 次 | `6E 80 BE` + 乱码（3 次运行 0/3 合法） | 乱码 |
| 连发 2 次，间隔 10 ms，等 50 ms | `6E 88 02 00 60 00 00 0E 00 0F D5`（3/3） | 乱码 |
| 同上，等 100 ms | 合法（2/2） | 乱码 |
| 同上，读 VCP `0x10` 亮度 | 合法 2/3，当前 `0x64`、最大 `0x64` | 乱码 |

结论：

- **P275MV 只收到一次请求时回 Null Message（`6E 80 BE`），连发两次才回值。** 这与 MonitorControl 在 Apple Silicon 上的做法一致。
- Null Message 只有 3 字节，缓冲区其余部分是总线残留；之前把尾部当成「上次回包的残片」是误判。
- 不重发请求而再读，读到的不是回包而是残留数据。所以「读到 Null Message 只再读、不重写」是错的，每次重试都要重新发请求。
- 偶发失败（亮度 1/3）靠整轮重试兜住。

### 修复与验证

`deskbaton_ddc_transact`：在同一 `IOAVService` 上把请求连发 2 次（每次前等 10 ms），等 50 ms 读一次；Rust 侧把 Null Message 归为未就绪，整轮最多重试 3 次。`set_input` 也改为连发 2 次（Set VCP 重复执行无副作用，但切换效果还没在本机实测）。

修复后连续 10 次 `deskbaton-cli get-input` 全部返回 `0x0F`。

HP D27k 尚未用新实现复测。

### 回包含义

| 字段 | 值 | 说明 |
|---|---|---|
| 当前值 | `0x0F` | 业界常见 **DP-1** 编码 |
| 最大值 | `0x0E` | 小于当前值，不能当「合法编码上限」用 |
| 类型 | `0x00` | 显示器把 `0x60` 报成「设置参数」类型 |

## 对设计假设的含义

设计文档（§3）尚未验证的两项：

| 假设 | 本次观察 | 状态 |
|---|---|---|
| USB-C = `0x1B`，DP = `0x0F` | Mac 走 USB-C，读到 `0x0F` | **与常见值不符**。这台显示器很可能把 USB-C（DP Alt Mode）报成 DP。DP 口（Windows）的编码仍未知，两个口有可能撞码；撞码时「持棒判定」不成立。 |
| KVM 跟随输入源 | 切到 DP 后约 4 秒键鼠离开 Mac，并能操作 Windows；切回后回到 Mac | **成立** |
| 显示器只接受活跃输入口的 DDC | 画面在 DP 时，Mac 的 Get VCP 只收到 Null Message | 读取不成立；Set VCP 是否被接受未测 |

在 DP 口的编码读到之前，不改设计文档的默认 `input_code`。

## 用 OSD 手动切走再切回（22:22–22:25）

条件：Mac 合盖，Windows 处于睡眠；`deskbaton-cli stay-awake` 在切走前已被意外结束（后台进程随调试会话退出），所以本次**没有**任何防合盖睡眠措施；每秒记录也只留到 22:21:41。

依据 `pmset -g log` 和用户观察：

| 时间 | 事件 |
|---|---|
| 22:22:08 | 用户切到 DP；内核释放 USB 断言，键鼠离开 Mac |
| 切到 DP 期间 | 显示器显示「无信号」，键鼠无法唤醒睡眠中的 Windows |
| 全程 | 没有 Sleep / Wake 事件，Mac 没有睡眠（本机 `sleep 0`，`displaysleep 60`） |
| 22:24:42 | 用户切回 USB-C；Mac 记录「Display is turned off」，显示器显示无输入源 |
| 切回后 | 按键盘、动鼠标都没有点亮画面 |
| 22:24:59 | 开盖（`lidopen`），显示恢复 |

结论：

- **KVM 至少会把 USB 从 Mac 切走**。键鼠有没有到 Windows 这次看不出来：Windows 在睡眠，KVM 键盘也没能唤醒它。
- 切回后 Mac 关掉了显示输出，KVM 键鼠点不亮。当时判断「不是系统睡眠」，下一节的复测推翻了这一点。

## 第二次切走再切回：`stay-awake` 运行中（22:31–22:34）

条件：Mac 合盖，Windows 已唤醒；`deskbaton-cli stay-awake 600` 全程运行（IOKit 合盖睡眠控制 + 防空闲睡眠断言），后台脚本每秒记录。

| 时间 | 事件 |
|---|---|
| 22:32:14 | 切到 DP。Mac 发的 Get VCP 只收到 Null Message（非活跃输入口不回值），Mac 仍然看得到这台显示器 |
| 22:32:18 | 键鼠离开 Mac；**键鼠在 Windows 上可用，KVM 跟随输入源成立** |
| 22:33:02 | 用 OSD 切回 USB-C。「Display is turned off」，外接屏从 Mac 的列表里短暂消失（22:33:03） |
| **22:33:07** | **`Entering Sleep state due to 'Clamshell Sleep'`**，`stay-awake` 没拦住 |
| 22:33:50 | 开盖唤醒（`Wake ... due to ... lid`） |

修正上一节的结论：上一节没开 `stay-awake`，切回后 Mac 同样进入了睡眠流程（22:25:12 的「Delays to Sleep notifications」），只是开盖较早打断了它。**黑屏的原因就是合盖睡眠，触发点在切回时，不在切走时**：切走时 USB-C 链路还在，Mac 仍有外接屏；切回时 USB-C 重新协商，外接屏短暂消失，此时键鼠也还没回来，合盖模式的条件不满足。

### 为什么 IOKit 合盖睡眠控制无效

按 XNU（`iokit/Kernel/RootDomainUserClient.cpp`、`IOPMrootDomain.cpp`）和 powerd（`PowerManagement/pmconfigd/PMAssertions.c`）源码：

- `kPMSetClamshellSleepState` 写入的是 `clamshellSleepDisableMask` 中的 `kClamshellSleepDisablePowerd` 位。外接屏消失时，只有掩码为 0 才会合盖睡眠。
- powerd 自己也用这一位：`setClamshellSleepState()` 在桌面模式变化（外接屏插拔）时重新计算，并写入 `newState ? 1 : 0`。外接屏消失时它写 0，覆盖掉我们写的 1。
- 掩码归零时，XNU 在同一次调用里立即重新判断合盖状态并睡眠，事后再写回去来不及。
- 用户连接关闭不会重置这一位，也没有权限检查，所以普通用户调用返回成功，但效果会被 powerd 随时覆盖。
- 正规做法是给断言加 `AppliesOnLidClose`，powerd 会把它计入合盖判断，但这需要 Apple 私有 entitlement（`kIOPMAssertOnLidCloseEntitlement`），第三方程序拿不到。

剩下可行的做法：需要 root 的 `pmset -a disablesleep 1`（设计里原本的第二期回退路径），或者让外接屏在切换过程中始终存在（如 HDMI 假显示器插头）。

## 第三次切走再切回：`sudo pmset -a disablesleep 1`（22:47–22:50）

条件：Mac 合盖，Windows 醒着；`pmset -g` 显示 `SleepDisabled 1`；不运行 `stay-awake`。（22:44 那一轮命令没有生效，`SleepDisabled` 一直是 0，结果与前两轮相同，不计入。）

| 时间 | 事件 |
|---|---|
| 22:48:36 | 切到 DP，键鼠离开 Mac |
| 22:49:15 | 切回 USB-C，外接屏从 Mac 的列表里短暂消失 |
| 22:49:22 | 键鼠回到 Mac |
| 22:49:30 | 脚本执行 `caffeinate -u` |

`pmset -g log` 在整个过程中**没有 Sleep 事件，也没有「Display is turned off」**。不开盖画面就恢复了；因为显示输出一直没被关掉，恢复与 `caffeinate -u` 无关。

结论：`SleepDisabled` 能挡住切回时的合盖睡眠，验收清单第 1 项的前提成立。代价是需要 root，而且这是系统级持久设置，必须由程序负责恢复。

## 第四次：用 sudoers 规则实现的 `deskbaton-cli stay-awake`（23:02–23:04）

条件：Mac 合盖，`SleepDisabled` 由 `stay-awake` 经 sudoers 规则自动设置，`displaysleep 20`。切到 DP、约 1 分钟后切回：没有 Sleep 事件，不开盖画面恢复。与第三次结论一致。

## 第五、六次：Mac 显示输出已关闭后再切回（23:10–23:38）

条件：Mac 合盖，`stay-awake` 运行中（`SleepDisabled 1`），`displaysleep` 临时改为 1 分钟，让 Mac 在 Windows 持棒期间关闭显示输出。

**第五次**：在 Windows 停留约 2.5 分钟后切回，等约 10 秒并按键，画面不亮，只能开盖。

| 时间 | 事件 |
|---|---|
| 23:11:15 | 切到 DP，键鼠离开 Mac |
| 23:11:58 | Mac「Display is turned off」，系统没有睡眠 |
| 切回 USB-C 后 | 直到开盖，Mac 的 USB 树上都没有出现键盘 |
| 23:13:44 | 开盖，23:13:45 显示亮起 |
| 23:13:53 | 键鼠这才回到 Mac |

**第六次**：模拟 agent 流程，切走 2 分钟后脚本执行 `caffeinate -u -t 120`（与 `wake_display` 同为声明用户活动），用户在切走后 2:30–3:30 之间切回，等 30 秒，画面不亮。

| 时间 | 事件 |
|---|---|
| 23:34:06 | 切到 DP，键鼠离开 |
| 23:35:04 | 显示关闭 |
| 23:36:06 | `caffeinate -u` 执行，**合盖状态下显示亮起** |
| 23:36:37 | 显示又关闭（只亮了 31 秒，`caffeinate` 的 2 分钟断言仍在） |
| 23:37:48 | 开盖，显示亮起；23:37:55 键鼠回到 Mac |

结论与推断：

- `SleepDisabled` 生效时 Mac 不会睡，但 `displaysleep` 照常关闭显示输出。
- **推断（与三次失败、两次成功都吻合，未单独验证）**：P275MV 的 KVM 只在 USB-C 口有视频信号时才把 USB 交给 Mac。Mac 显示输出已关时切回，显示器收不到 USB-C 信号，KVM 不交出键鼠，按键也就点不亮 Mac，形成死循环。切回时显示输出开着的两次（第三、四次）都成功。
- 声明用户活动能在合盖时点亮已关闭的显示，但没有真实输入时只亮约 30 秒。
- 第六次的模拟与 agent 流程不等价：用户切回的窗口从 23:36:36 开始，显示 23:36:37 又关了，切回时大概率已经没有视频输出。日志区分不出 23:36:37 的关闭是 30 秒超时还是切回时 USB-C 重新协商造成的。真实交棒中 `wake_display` 在切输入源前 1–2 秒调用，这条路径还没实测。

候选修法（未实测，未改设计）：

- **交出控制权期间持有「防止显示器空闲睡眠」断言**，让 Mac 的显示输出一直开着。不需要 root，不依赖网络时序，手动 OSD 切换也能用。代价是 Mac 持续向显示器输出画面（用户看不到）。可先用 `caffeinate -d` 加 `stay-awake` 验证。
- 只依赖 agent 流程中的 `wake_display`：手动 OSD 切换不受保护，且要确认切换前那 1–2 秒里显示确实已经点亮。
