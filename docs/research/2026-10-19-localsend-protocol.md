# LocalSend 传输协议调研

日期：2026-10-19

来源：[LocalSend Protocol v2.2](https://github.com/localsend/protocol/blob/main/README.md)（官方协议仓库 README）。只借鉴协议思路，不引用其代码。

## 1. 结论

DeskBaton 文件快传借鉴 LocalSend 的**会话模型**：先发元数据由接收方决定，接收方下发令牌，发送方凭令牌上传，任一方可取消。不照搬它的 HTTP 服务和组播发现：DeskBaton 已有 mDNS 发现、配对与证书指纹固定的 TLS 链路，另开 HTTP 端口只会多一条防火墙规则和一套重复的信任校验。

## 2. 协议要点

| 项 | LocalSend v2 | 对 DeskBaton 的意义 |
|---|---|---|
| 端口 | TCP / UDP 53317，组播 `224.0.0.167` | 不需要；复用 47800 |
| 加密与身份 | HTTPS 自签证书；指纹 = 证书 SHA-256，用于记住设备、避免自发现 | 已有同样的指纹，且已固定到设备档案 |
| 发现 | 组播公告 + `POST /register` 回应；组播失败时逐 IP 扫描 | 已有 mDNS |
| 准备 | `POST /prepare-upload`：`info` + `files{id → fileName,size,fileType,sha256?,preview?}`。接收方可全收、部分收、拒绝；返回 `sessionId` 和每个文件的 `token` | 借鉴：请求 → 同意 → 一次性令牌 |
| 准备的错误码 | 204 无需传输 / 401 PIN / 403 拒绝 / 409 被另一会话占用 / 429 请求过多 | 拒绝原因做成枚举；不做「同一时刻只有一个会话」 |
| 上传 | `POST /upload?sessionId&fileId&token`，请求体为原始字节；**可并行**；提供了 `sha256` 时接收方校验，不符回 422 | 改为一条连接上按顺序流式发送；哈希在文件末尾给出，不需要发送方先通读一遍 |
| 取消 | `POST /cancel?sessionId` | 借鉴，双向都可取消 |
| 反向传输 | 发送方起 HTTP 服务，接收方用浏览器下载（明文 HTTP，因浏览器不接受自签证书） | 不需要：两端都装 DeskBaton |
| PIN | 可选 `?pin=` | 不需要：配对已建立信任 |
| 续传 | 协议未定义 | 首版同样不做 |
| 文件夹 | 协议未定义目录结构 | 自行定义清单中的相对路径 |

## 3. 不借鉴的部分与原因

- **准备阶段携带完整文件列表**：控制帧上限 1 MiB，上万个文件的文件夹清单可能超限。DeskBaton 请求只带摘要，完整清单在同意后从文件连接下发。
- **`prepare-upload` 阻塞等待用户决定**：HTTP 请求一直挂着，发送方不知道对方是否在场。DeskBaton 的请求是异步消息，挂起状态由两端面板各自展示。
- **按文件并行上传**：局域网里单条 TCP 已能跑满带宽，按顺序发送更容易做进度和失败统计；多个会话之间仍然并行。
